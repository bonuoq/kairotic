# The studies

*[Leer en castellano](studies.es.md)* · [Documentation](README.md)

Kairotic was built as a series of **studies**: each one a question, answered by a working page
published as a claude.ai artifact, and kept as it was in [`studies/`](../studies). Studies 1–8 were
written in Spanish; from Study 9 on, code and interface are in English (the [glossary](glossary.md)
maps the old names to the new ones). From 0.1.0-alpha on, the app lives in [`app/`](../app) and grows
as one.

**Opening a study.** Kairotic Pages serves every study at its folder:
`https://bonuoq.github.io/kairotic/studies/<folder>/`, for example
[`studies/29-live/`](https://bonuoq.github.io/kairotic/studies/29-live/). There a study can use what a
page published on claude.ai cannot, such as the microphone. On your own computer, serve the folder and
open it on `localhost` (a page opened as a file cannot load its modules):

```sh
cd studies && python3 -m http.server 8000     # then http://localhost:8000/29-live/
```

| 2 | History | collaborative event tree, front, simultaneity, merging, rooms |
| 3 | Score | piano roll and notation (Verovio) synchronised by time ⇄ space |
| 4 | Patch | editors as patch boxes, one voice per box |
| 5 | Canvas | frequency × time, grids and Scala; reader, ramp, steps; message engine |
| 6 | Components | component registry; code boxes: faust~ and script |
| 7 | Library | components defined in the work, shared library, importing |
| 8 | Controls | a component's own view: knobs playing a faust~ |
| 9 | Sections | everything in English; components in sections (`:args`, logic, `:view` template) |
| 10 | Subpatches | patches inside patches: `patch` boxes with `inlet`/`outlet`, abstractions with `$1`, `(abstract …)` |
| 11 | Presentation | a performer's view (`(present …)`, Present button) and sub-patches seen as panels of their controls |
| 12 | Space | a generic `canvas` read along X or Y (and `freqt` for frequency over time); `dac~` with real channels, `pan~`, binaural `space~` |
| 13 | Signal | reading at audio rate (`phasor~` → `reader~`, an AudioWorklet; signals into `osc~`/`gain~` parameters) and along 2D paths (`reader path`); per-voice gates (`reader~ 2 gate`) into envelopes (`adsr~`); boxes edited from the patch (inspector), and gestures that rewrite the box text |
| 14 | Packages | official packages by category (`@kairotic/synth`: adsr~, synth~ · `@kairotic/spatial`: pan~, space~), brought into a work when one of their classes is written; the Kairotic API (`api/…`) for components |
| 15 | Claude | components written with Claude inside the work (the Claude tab, `(ask-component …)`), on the viewer's own Claude account; Claude tries what it writes with the page's tools before it arrives as a component box |
| 16 | Faust | Claude also writes Faust (compiling it to check it), abstractions with faust~ boxes and knobs, and bpatchers whose instances show their knobs as a panel; a catalog of examples by category that Claude reads with a tool ([examples/](../examples/README.md)) |
| 17 | Pages | the same page outside claude.ai: a backend adapter (db, rooms, user, Claude) so it runs on GitHub Pages with [GUN](https://gun.eco) rooms through a [relay](../relay/README.md) and Claude with each person's own Anthropic API key ([docs/pages.md](pages.md)) |
| 18 | Learn | the Help tab: what each class does, inlet by inlet, with a help patch (**?** on a selected box, `:help` in a component); tutorials in Spanish and English that open as lessons — each step a point of the history, ◀ ▶ between steps, a branch of your own when you change something ([docs/tutorials/](tutorials/README.md)) |
| 19 | Time | music as data: musical trees in EDN (hiccup, like bach's llll) with measures, tuplets, chords, dynamics, articulations, texts, parameter changes and reusable fragments; `tree` and `mt` boxes write, transform (transpose, invert, retrograde, augment, canon…) and play them; a score, freqt or canvas shows them live; a theory tutorial ([docs/mt.md](mt.md)) |
| 20 | Work | the work as a tree: a `:piece` of `:section`s, each with its voices (a staff per voice across sections, section names, double bars); a tree box's history is made of node edits (`tree-edit!`, and the text editor or `tree!` write only the difference), so branches that change different nodes merge; scores edit the tree (click a note: ↑ ↓ + − ← → Delete); a composition tutorial |
| 21 | Flow | data that flows: messages travel without ▶ (▶ is for sound and time); a tree sends itself when it changes (or the patch around it does); a score sends the edits made on it by a third outlet, back to the tree by a dashed line; loops without time are cut and reported ([docs/flow.md](flow.md)) |
| 22 | Embed | Kairotic inside other pages (Notion, a blog): links that carry a patch (its code, compressed, read as data), a tutorial step or a help patch; `?embed` shows only the patch, `?present` only its presentation, filling the frame, with a fullscreen button; the Embed button and `(embed-link)` ([docs/embed.md](embed.md)) |
| 23 | Ask | the Claude tab makes patches from a description, or changes the open one, checked with the page's tools (classes, ports, Faust, components) and loaded as one event; `?ask=` links carry a description — never a key — and whoever opens them makes the patch with their own Claude ([docs/ask.md](ask.md)) |
| 24 | Draw | one buffer, two renderers: a `freqt` drawn as SVG (with thi.ng/geom) over a WebGL spectrum made from the same strokes |
| 25 | Overlay | graphic marks on a Verovio score, stored in beats and staff steps so they follow its reflow; a `monitor` of incoming messages (descriptors with Meyda) — now in `@kairotic/analysis` |
| 26 | Layers | components drawn in SVG only; layers over or under the patch with marks anchored to boxes and projections of a box's view; one WebGL background for the whole patch (left for later) — layers are in the app from 0.2.0-alpha |
| 27 | Geometry | a score seen as music theory: pitch-class clock, Fourier coefficients and Tonnetz path; new shapes `:opacity`, `:curve`, `:group`, `:hit` — now `@kairotic/theory` and `kairotic.shapes` |
| 28 | Shift | a sound pitch-shifted offline into a new buffer with [stftPitchShift](https://github.com/jurihock/stftPitchShift) (C++, MIT) built to WebAssembly with wasi-sdk, in a worker; factors read as music (ratios, semitones, cents), several at once as a chord, changing over time as a progression; formant preservation; the new buffer keeps its recipe (source by hash and the shift as data), and remaking it from the recipe gives the same hash |
| 29 | Live | `shift~` in real time: the same WebAssembly as Study 28, frame by frame inside an AudioWorklet (one frame of latency, about 5% of a core with a chord and formants at overlap 8), its output equal to the offline shift; chords, looped progressions on the audio clock, live transposition and formants; what a work keeps of a take is the stream of messages to `shift~`, logged on the audio clock |
| 30 | Inverse | inverse synthesis, first step: a bank of random patches of one synth (plain JavaScript, so the same seed gives the same samples in the page, a worker or Node) analysed with Meyda as `features~` does, exported as NDJSON (`generate.mjs` makes large banks in Node); a first way back — the nearest neighbour in descriptor space — measured against a random pick, by descriptor distance and by patch distance |
| 31 | Units | a `faust~` box opened as a patch of Faust's own elements (`@kairotic/faust-units`: primitives, controls, library functions, `in`/`out`) beside its code, one piece of data in two views: a patch gives code (one definition per box, loops through the one-sample delay `'` written with `~`, the layout in a last comment) and code gives a patch (read with Faust's block-diagram algebra; what the boxes do not know becomes a box of code with the inputs and outputs the compiler finds); round trip checked sample by sample (`tests/roundtrip.mjs`) |
| 32 | Learn | the way back learnt: a bank of patches that sound (silences and clicks drawn again), a small network in plain JS (descriptors over 8 moments and the pitch YIN hears → the 10 parameters) trained in a worker, which can then learn to listen (through a second network that imitates the synth, its error about how its patch would sound), and CMA-ES that refines its guess by rendering, with the pitch held where YIN heard it (after Engel et al. 2020); on 40 targets the network on its numbers sounds at 0.443, the listening one at 0.335, a search of 100 renders from it at 0.254 and one of 400 at about 0.19 (nearest neighbour 0.341, floor 0.120), with the right note in 22 of the 23 targets that have one |
| 33 | Lines | a work as a **project** of several history lines (discussion #117), each a whole tree of its own shown as a tab above the patcher; `patch @name` is the line `name` as a sub-patch (its `inlet`/`outlet` boxes as ports), **following** it (the line at its front, its newest point) or **pinned** to a point of its history; lines nest and cycles are refused; an embedded `patch` **extracted** to a line with the history it had inside its box, a reference **inlined** back; renaming rewrites the users (older points find the old name); a **release** takes the main line and every line it reaches, each at the point it uses, all pinned (a line used at two points becomes two); lines exported and imported with their history; a help project with one tab per view of a topic (`tests/model.html`) |
| 34 | IO | Kairotic talking to the outside, first step (discussion #135): one **event format** for whatever comes in or goes out — an EDN map in the shape of a pattern event (`:freq` in Hz, `:amp`, `:id`, `:gate`; `:glide`, `:cc`, `:pressure`, MIDI transport) — and MIDI in and out of it with Web MIDI: bend ranges read from RPN 0, **MPE** out (a channel per note, its exact Hz as a key plus a bend, the MPE Configuration Message) so microtones and just intervals reach hardware unrounded, or plain (one channel, rounded); snapshots of a player or a keyboard as note events; a phone's **motion** (tilt smoothed and sent only when it moves, shake as a trigger; iOS asks permission on a click) and **gamepads** (read every frame, differences as events, standard names, dead zones) as events of the same format, and playing with them: tilt as pitch and loudness, shake to start and stop, pad buttons as a pentatonic with the stick as a bend — through the same MPE out as everything; **OSC** through the relay (`npx @kairotic/relay --osc`, an OSC bridge on `ws://…/osc` with OSC 1.0 in plain Node, sending only to the targets it was started with and only for the sites it allows): every event out as `/kairotic/note`, `/glide`, `/cc`, `/tilt`, `/pad/…` and the same addresses back in as events, any other address as `{:type :osc …}`, OSC address patterns to choose what comes in, a SuperCollider example (`supercollider.scd`), tested against a live relay in CI; a **board** on a serial port (Web Serial: lines of numbers or `key:value` as events); the page's parameters published as **OSCQuery** by the relay and set from outside; a **room** (relay 0.3 `/signal`): the stream of events between pages over WebRTC data channels (through the relay while none is open) and a **shared clock** (offset to the relay's time from the shortest round trips), a tempo started on one page on the same beat on all, with a metronome; a take recorded as **freqt** data (glides as staircases, amp as weight); a keyboard of the page and a **loopback** to try it without hardware or Web MIDI; its tests run in CI with `tests/studies.mjs` |
| 35 | Recipe | a sound → the values of a `faust~`'s sliders that sound closest → a recipe: the code's own sliders are the parameters (a log scale where it says `[scale:log]`), rendered offline from the compiled WebAssembly through the DSP's own interface (whatever libfaust compiled it); a small bank of random settings gives the distance's statistics and the first guess; the pitch, on a slider called `pitch` or `freq`, is held where YIN hears it, at the octave that sounds closest; CMA-ES does the rest, comparing levels apart from loudness so a recording at any level can be matched; the recipe is the same code with the values found, ready for a `faust~` box. Settings of the Faust twin of Study 30's synth are found back at 0.34 against 0.86 for the nearest random setting, patches of the JS synth at 0.36 against 0.71 |
| 36 | Talk | talking in a room (discussion #135, `@kairotic/net`): **text** on a reliable WebRTC data channel, anchored by what it writes (`@b3` a box, `#12` a point of the history, `^33` a beat); **push-to-talk** (an audio track on every connection from the start, so the microphone sounds only while held, with no renegotiation); **voice notes** (MediaRecorder, sent in pieces checked by hash); **video**, optional and small (320×240, 15 fps, silent). All of it **ephemeral until someone keeps it**: a message as an annotation, a voice note as a sound (decoded, hashed and stored in IndexedDB `kairotic-sounds` as the app keeps recorded audio, so it is a sample there), a frame as an image; what is yours is kept at once, keeping what is someone else's asks them (Allow / Decline), and what someone said in a session that has left cannot be kept; a kept thing says who made it and who kept it |
| 37 | Notation | descriptors as a score (discussion #114): four lanes over time — **pitch** (MIDI), **loudness** (dB), **brightness** (the spectral centroid, Hz) and **noisiness** (the spectral flatness) — drawn with the pointer or read from a sound file as `features~` and `pitch~` hear it, and **realised by a `faust~`**: its `pitch` and `gain` sliders follow their lanes, its other sliders are chosen frame by frame from a bank of its own steady settings, heard, for the brightness and noisiness written (where a pitch is written, among the settings in which YIN would hear it); then it listens to what it played and asks for more where it fell short (three passes). Over four scores, a note of another instrument (the Faust twin of Study 30's synth) and the voice's own moving sliders, what sounds is off by 0.3 dB, 2.2 semitones of brightness, 0.014 of noisiness and about 10 cents on average, against 5.0 dB, 7.3 semitones and 0.022 for the voice held still at the mean of what is written. Not every score can be played: noisiness and brightness are tied in a voice (noise as dark as a tone does not exist in it), and the page shades the frames that ask for what the voice cannot do |
| 38 | Futuribles | the possible futures of a work beside its history (discussion #172): the **history** keeps only choices (yours or the engine's, with their branches); the **futuribles** are never stored, a pure function of a point of it and a **rule set** as data, and a choice is the only bridge between the two. First domain: a **canon** at a diatonic interval and a delay (the comes is the dux d notes later, shifted, so every rule between the voices falls on the dux against itself), first species after Fux: hard rules that make a note legal or not with a reason, soft ones that give it a cost — leaps are not penalised, only compensated by contrary motion (a 4th or a 5th turns back), and what costs is a line that stays still, hovers, runs one way or repeats itself mechanically, with the **memory of the work** (a figure used earlier costs less); **invertible counterpoint** as a transform of the voices checked by the same rules (at the 10th parallel 3rds become octaves, at the 12th a 6th becomes a 7th); **obligations** the next notes owe (turn back after a leap, end on the final). Hard rules look only at the last notes, so the ways to finish from any point are **counted exactly** (memoized on that window): their log₂ is the **divergence**, the bits of freedom left, drawn under the score, and the fan of futuribles shows each next note with its futures, the dead ends and why the others are not allowed; **why?** counts the futures again without each hard rule, to show which one closes a note or a point. The engine chooses only among notes with a future (never stuck), weighing each with the cheapest way the line can go on for the next notes (it **looks ahead**), with a seed and a **temperature** that can follow the divergence as in Copycat. A dorian canon at the octave below, two notes later, 12 notes: 15723 canons; in Scittle the engine writes one in about 30 ms, with 1% repeated notes and 38% leaps |
